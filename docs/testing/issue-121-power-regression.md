# Issue 121: バッテリー消費・発熱回帰の計測手順

## 目的

録音待機、録音中、推論中、推論後の4状態を同じ条件で測定し、CPU・メモリ・推論時間・消費電力の回帰を切り分ける。原因が特定できるまでは、既定値や自動停止の仕様を変更しない。

## 比較条件

- 同じMac、電源状態、外部ディスプレイ構成、OS、アプリ版を使う
- `gpuAccelerationEnabled` と `keepBackendReadyInBackground` の組み合わせを記録する
- 同じ固定音声を各条件で3回以上再生する
- 起動直後のモデル準備と、十分に待機した後の状態を分ける
- 文字起こし結果、空結果、エラー、推論時間を同時に記録する

## 状態ごとの計測

1. アプリ起動後、録音も推論も行わず5分待機する
2. 10秒程度の同じ音声を録音する
3. 固定音声を推論し、完了までの時間と結果を記録する
4. 推論完了後、5分待機して復帰状態を確認する
5. 各状態でアプリ本体と子プロセスのCPU、RSS、物理フットプリントを取得する
6. `sample` でCPU busy loop、音声処理、モデルロード、プロセス待機のどれが支配的かを確認する
7. `powermetrics` が利用できない場合は、消費電力を推定せず `NOT_RUN` と記録する

プロセスツリーの反復測定には、次の診断ツールを使える。出力にはPID、コマンド、パス、ホスト情報を含めない。

```sh
uv run python tools/measure_process_activity.py --pid <root-pid> --duration 300 --interval 1
```

`READY` はroot processを検出して測定したこと、`NOT_RUN` は対象が見つからなかったこと、`ERROR` はプロセス一覧を取得できなかったことを示す。結果の `cpu_percent` はプロセスツリーのCPU合計、`rss_kib` はRSS合計で、各々p50/p95/maxを返す。root PID自体は結果に記録しない。

集計対象のprocess groupは、rootが継承した共有groupを所有境界として扱わず、rootがgroup leaderである専用groupと、rootとは異なる子孫processのgroupだけを保持する。backendが専用groupへ移動した後に孤児化しても、同じgroupのCPU/RSSを後続サンプルへ含めるためである。これにより、シェルなどrootと同じ共有groupにいる無関係なprocessが集計へ混入することを防ぐ。

共有groupを継承した子孫だけが孤児化した場合は、rootが存在した時点で観測した経過時間と一致する子孫だけを後続サンプルへ含める。共有group全体は集計せず、同じPIDでも経過時間が若返ったものはPID再利用として除外するため、無関係なprocessの混入を避けながら停止確認の見逃しを防ぐ。

停止処理後に対象root processが残っていないことを確認する場合は、次を使う。

```sh
uv run python tools/measure_process_activity.py --pid <root-pid> --wait-for-exit --timeout 30 --interval 1
```

`EXITED` は監視中にroot processと、root配下で観測したprocess groupのメンバー、および経過時間で確認できる孤児子孫が消えたこと、`STILL_RUNNING` はtimeoutまでそれらのいずれかが残ったことを示す。開始時点で対象が見つからない場合は `NOT_RUN` となる。監視中に同じPIDの経過時間が若返った場合は、PID再利用として `ERROR`（`root_process_reused`）を返し、元のプロセスの終了を成功扱いしない。このモードもPID、コマンド、パス、ホスト情報を結果に含めない。

プロセス確認の例（プロセスID、パス、音声本文は記録結果に残さない）。

```sh
app_pid="$(pgrep -x KotoType | head -n 1)"
ps -axo pid=,ppid=,%cpu=,rss=,etime=,command= |
  awk -v p="$app_pid" '$1 == p || $2 == p'
sample "$app_pid" 1 1
```

## 固定音声の推論基準値

2026-08-25 に、ローカルに保持した固定音声11ケースをMLX backendで各1回実行した。これはアプリの子プロセスを直接測るものではなく、推論中の比較用基準値である。

| 戦略 | mean CER | 誤挿入率 | 脱落率 | 推論 p50 | 推論 p95 | 平均RTF |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `none` | 0.400 | 100% | 0% | 0.517秒 | 0.534秒 | 0.143 |
| `ffmpeg_office_gate` | 0.400 | 20% | 0% | 0.532秒 | 0.559秒 | 0.148 |

- `ffmpeg_office_gate` は誤挿入を減らしたが、推論p50は `none` より約3%遅かった
- `/usr/bin/time -l` のプロセス最大RSSは、単一戦略実行で約1.35GiB、両戦略の同一実行で約1.71GiBだった。モデルロードを含むため、アプリ常駐時のRSSとは比較しない
- 初回ロード込みの実時間は単一戦略実行で21.4秒だった。電力は権限なしのため `NOT_RUN` とした
- 文字起こし精度の改善や発熱原因の特定を意味しないため、既定値変更の根拠にはしない

同じ固定音声1件をCPU backendでも実行したところ、モデル準備0.98秒、推論4.28秒、最大RSS約2.31GiBだった。これはbackend選択の参考値であり、アプリの常駐メモリやバッテリー消費の測定ではない。

さらに、現行backendプロセスへ同じ固定音声を実際のJSONリクエストとして送り、GPU経路を測定した。モデル事前準備は0.592秒、リクエスト完了まで3.251秒、backendプロセスのCPUはp50 56.1%・p95 83.8%、RSSは約1.62〜1.72GiBだった。待機時のCPU 0.0%観測との差は確認できたが、GPU側の電力値は取得していないため、発熱・バッテリー消費の原因とはまだ断定しない。

同じbackend probe後の5秒間を比較すると、`preload_model=true` は待機RSS中央値約1.10GiB（約1.09〜1.19GiB）、`preload_model=false` は約164MBだった。両条件ともprobe後の待機CPU中央値は0.0%だった。これはbackend単体の比較であり、アプリ設定の保存・worker構成や実機の電力値を直接測った結果ではない。

同じ手順をCPU backendでも実行した結果は、CPU+preloadで待機RSS中央値約1.77GiB、CPU+no-preloadで約164MBだった。待機CPU中央値はいずれも0.0%だった。GPU/CPUの両方で、preloadを有効にすると約1GiB以上のモデル常駐メモリ差が再現できた。

現行Swift側では、`keepBackendReadyInBackground` の既定値を `true` のまま維持している。設定が `false` の場合は待機用workerを常駐させない経路になる。設定JSONの保存値と既定値の扱いはテストで確認するが、AppDelegateからbackendを起動・停止する実機ライフサイクルは別のE2E確認が必要である。

停止処理については、`PythonProcessManager.stop()` が検証済みのbackend専用プロセスグループへSIGTERM/SIGKILLを送り、handshakeを取得できない場合だけ従来のroot/子孫ツリー停止へフォールバックする。Swiftユニットテストはcontrol messageの形式を、Pythonユニットテストは専用グループ確立とhandshake出力を確認する。停止完了は上記の`--wait-for-exit`診断で実プロセスとして確認する。これは開発用Python経路の実プロセス検証であり、同梱backend、AppDelegateの実マイク経路、GPU処理完了後の電力状態までは検証しない。

さらに、停止対象がすでに終了している場合はプロセスツリーへシグナルを送らないガードを追加した。終了済み `Process` が保持していたPIDが別プロセスへ再利用された場合に、無関係なプロセスを終了させるリスクを避けるためである。この判定はユニットテストで確認している。

backendは起動直後に専用のプロセスグループを確立し、Swift側は停止時にそのグループも終了させる。これによりbackend rootが先に終了して子プロセスが孤児化した場合も、rootのPIDツリーだけに依存せず停止を試みる。プロセスグループ確立に失敗した場合は従来のプロセスツリー停止を使い、起動失敗にしない。

さらに、親アプリの消失をbackendのwatchdogが検知した場合も、状態ファイルの解除後に同じプロセスグループへSIGTERMを送り、短い猶予後にSIGKILLを送る。これによりアプリの異常終了時にもbackendの子プロセスが残り続ける経路を閉じる。グループ確立に失敗した場合は従来どおりbackend自身の終了と状態解除のみを行う。

4条件のbackend単体基準値は次の通りである。

| GPU設定 | preload | effective backend | 待機RSS中央値 | 待機CPU中央値 |
| --- | --- | --- | ---: | ---: |
| on | on | MLX | 約1.10GiB | 0.0% |
| on | off | MLX | 約164MB | 0.0% |
| off | on | CPU | 約1.77GiB | 0.0% |
| off | off | CPU | 約164MB | 0.0% |

この表は同一ホスト上のbackend単体測定であり、アプリの保存設定や実機バッテリー消費の比較結果ではない。

## 判定

## 実アプリ待機状態の測定（2026-08-27 JST）

録音・推論を開始せずに実行中のKotoTypeアプリを8秒間、1秒間隔で測定した。出力はプロセス識別子を含まない集計値のみである。

| 状態 | サンプル数 | プロセス数最大 | CPU p50/p95/max | RSS p50/p95/max | 電力 |
| --- | ---: | ---: | ---: | ---: | --- |
| アプリ待機 | 9 | 3 | 0.30% / 1.50% / 1.50% | 69,408 KiB / 69,408 KiB / 69,408 KiB | NOT_RUN |

- rootプロセスは9サンプルすべてで検出された
- 待機中のプロセスツリーに高いCPU使用率の継続は観測されなかった
- `sample` による1秒間のスタック採取は実行できたが、単一サンプルだけで発熱原因を特定するものではない
- `powermetrics` は管理者権限が必要なため、今回の電力値は `NOT_RUN` とした
- `make test-real-audio-capture` は入力デバイスなしのため `NOT_RUN`（終了コード2）となり、録音状態の測定とAVAudioEngine開始は行っていない
- この結果は待機状態だけであり、録音中・推論中・推論後の比較やバッテリー消費量を示さない

各条件について、次の項目を表にする。

| 条件 | CPU p50/p95 | RSS | peak footprint | 推論時間 | 結果保持 | 電力計測 |
| --- | ---: | ---: | ---: | ---: | --- | --- |
| 待機 |  |  |  |  |  | READY / NOT_RUN |
| 録音 |  |  |  |  |  | READY / NOT_RUN |
| 推論 |  |  |  |  |  | READY / NOT_RUN |
| 復帰待機 |  |  |  |  |  | READY / NOT_RUN |

改善を採用する条件は以下とする。

- 同じ音声の文字起こし結果と空結果率を悪化させない
- CPU、メモリ、推論時間、または電力の改善を変更前後で確認できる
- 録音停止、再録音、backend復旧に新しい失敗がない
- 電力計測が `NOT_RUN` の場合、電力改善を主張しない
- 実機条件が揃わない場合、結論を `NOT_RUN` または「再現せず」と明記する

Issue や PR に結果を記録する場合も、音声本文、認証情報、プロセスID、個人を特定できるパスなどは含めない。
